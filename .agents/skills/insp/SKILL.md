	- 예외: 세션 채팅의 답 · 짧은 조회(git log · grep · 파일 몇 줄 읽기) · flowtree 상태 명령(start · done · survey-ack 같은 한 줄)은 세션이 직접
- **작업 중심 = flowtree · hand_off · WORKLOG**(세션끼리 대화 최소 — 유저가 대화에 끼어들 수 있게): 할 일 · 진행 상태는 flowtree(작업 · 검증 · 질문 · 설문 노드와 inbox — 진행의 정본)로 주고받는다 · hand_off = 설계 상세 · 수정 범위 승인 · 검증 기록 · 결정 이유 · 섹션 작업 순서(채점 모델이 읽고 후임자가 이어받는 문서 · 진행 기록 표는 섹션이 끝날 때 flowtree 결과를 옮겨 적는 칸) · 인계는 WORKLOG 인계 칸 · 세션 사이 글(hub.py send · 붙여 넣기)은 유저가 시킬 때만

	- flowtree 는 flowtree.py 명령으로만 쓴다(잠금 → 다시 읽기 → 고침 → 교체가 들어 있다) · tree.json 을 직접 열어 고치지 않는다
	- 문서마다 쓰는 쪽이 정해져 있다: hand_off 본문 = MAIN 의 서브 · hand_off 검증 기록 · 코드 개선 제안 칸 = INSP 의 서브 · WORKLOG = 덧붙이기만(한 덩어리를 >> 한 번으로 · 기존 줄 수정 금지) · 결정 · 답 칸은 그 칸 주인만

	- md 를 고칠 땐 고치기 직전에 다시 읽고 바꿀 구간만 패치 · 패치가 «문맥이 안 맞음» 으로 실패하면 남이 먼저 고친 것 — 다시 읽고 다시 적용한다(통째로 다시 쓰지 않는다)
	- 고친 즉시 그 파일만 커밋 · 커밋 전에 git diff 로 내가 안 쓴 변경이 섞였는지 본다(섞였으면 그 줄은 그대로 두고 내 변경만) — 사라져도 git 에서 되살린다
- 제출 양식 문서(HOW_TO_RUN · AI_COLLABORATION)는 유저가 직접 쓴다 — 에이전트는 쓰지 않고 초안도 만들지 않는다
- **배포는 컨테이너(Docker)**: 결과물을 컨테이너로 띄워 실행 · 제출해야 한다 — 양식 lib/deploy(Dockerfile · compose · .dockerignore) · 계획 docs/DEPLOY_PLAN.md · 점검 $ready-end R8 · 뼈대 K0 + hand_off 섹션 목록에 컨테이너 섹션을 처음부터 넣는다

- 유저 = 응시자 · 결정 · 승인

- MAIN = 계획 · 지시(구현은 서브) · 2ND = 유저 보조(저장소에 쓰지 않음) · 서브는 «코드 수정 금지 · 서브를 또 띄우지 않는다» 를 지시에 넣는다(공통 절 대로)

## 1-2. flowtree 읽기 요령(그리기는 MAIN 몫 · 그리기 전엔 inbox 가 비어 있다)
- 할 일 = flowtree.py --role insp inbox(미검증 · 대상이 다시 done 된 검증 노드) · 세션끼리 글로 묻지 않는다
- 검증 노드 본문 = «섹션번호 · 단계 · 범위 · 볼 파일»(짧게 · 결정 이유는 hand_off 번호) → verify-start → 서브 지시(2-2) → 서브 커밋 · 재현 스크립트를 한 번 다시 돌려 확인 → run <검증> pass|fail "근거(커밋 해시 · 시험 명령 · 불일치 N건)" · 막히면 verify-hold <검증> "사유"
- 마법봉($insp-magic)은 검증 노드만 받는다(작업 노드는 대상 아님) · INSP 의 비정상이 MAIN 의 완료를 지우지 않는다(둘 다 보임 · 판정은 유저)

## 1-3. 세션 운영
- 세션은 MAIN · INSP · 2ND 셋 · 새로 열지 않고 압축만($hand-off → /compact → $hand-on · 시점은 유저) · 닉네임으로 부른다(같은 이름으로 새 세션 · 서브를 만들지 않는다)
- 허브: 시작 때 $codex-hub 로 붙기(--nick insp) · 섹션 검증이 끝나면 hub.py log · 🪄 로 시작하고 끝 줄이 «$insp-magic 요청id» 인 글이 오면 그 스킬(본문 = 유저 지시)
- 세션끼리 주고받기 = **flowtree · hand_off · WORKLOG 로**(2026-11-03 유저 지정 — 세션끼리 대화하면 유저가 끼어들 수 없다): 검증 요청은 inbox 의 검증 노드로 받고, 결과는 run 명령 · hand_off 검증 기록으로 남긴다 — MAIN 에게 따로 회신 글을 쓰지 않는다
	- 세션에 글 보내기 = python3 ~/.codex/skills/codex-hub/hub.py send --to <이름> '글'(글 앞에 @보낸이름 자동 · 작은따옴표 · 샌드박스에서 막히면 밖 승인 · 성공해도 «보냄» 까지만 보고) — 유저가 시킨 그 한 번만
- 검증 왕복: inbox → 검증 노드 → verify-start → **서브에게 검증 지시(2-2)** → 서브가 hand_off 검증 기록 · 개선 제안 · 재현 스크립트를 쓰고 커밋 → 내가 재현 스크립트를 한 번 다시 돌려 확인 → run
- 시험 대상: 시작할 때 git status --short 를 검증 기록에 남긴다 · 요청의 «볼 파일» 에 MAIN 미커밋 변경이 있으면 시험하지 않고 «검증 불가 — MAIN 미커밋(파일)» 으로 회신
- 재검증(대상 작업이 다시 done 되어 검증 노드가 inbox 에 다시 뜨면)은 그 재현 스크립트를 서브가 다시 돌려 상세 기록 일치 🟢 · 커밋 → 내가 확인 뒤 run(🔴 필수 지적만 온다)
- 예방: 저장소에 쓰는 세션이 늘면 같은 파일을 동시에 고쳐 충돌한다 → 내가 쓰는 곳은 위 세 곳뿐

## 1-4. 검증 단위 — 위험도
- 민감(데이터 파이프라인 · 외부 API · DB 쓰기) 섹션은 단계마다 검증 요청이 온다 · 저위험(UI 객체 · 배치 · 스타일)은 섹션 단위
- 지적은 MAIN 이 모아서 처리한다 · 다음 단계가 지적받은 코드를 그대로 쓰면 바로 고칠 것이라 그런 지적은 «다음 단계가 이 코드를 씀» 으로 표시

## 1-8. 시간 말고 실패 신호로 멈춘다
- 성공/실패는 종료코드 · 예외 · 에러 로그로 판정한다 · 경과 시간을 판정 기준으로 쓰지 않는다
- 오래 걸리는 스크립트는 단계마다 진행 한 줄을 출력한다 · 백그라운드 터미널은 /ps 로 상태 · /stop 으로 정지
- 외부 호출 대기 한도(timeout)는 CODE_RULE 5절
- 예방: 문제가 생겨도 제한 시간까지 조용히 기다리며 시간을 버린다

## 1-9. 기존 코드가 들어 있는 과제
- 기존 테스트 통과 ≠ 정답 · 성공 기준(C 번호)마다 결과를 직접 보는 테스트가 있는지 본다
- 업무 규칙은 코드에서 짐작하지 않는다(코드는 지금 동작만 · 지도 근거 [코드] · 기존 코드가 버그일 수 있다)

## 2-1. 늘 보는 검사
- 처음부터 실행: 새 venv · 빈 DB 로 설치 → 실행 → 화면까지(제출물도 처음부터 돈다)

## 2-2. 검증 서브 지시 · 판정(검증 노드를 받으면)
- **코드를 고치지 않는다.** 서브가 쓰는 곳 = hand_off 검증 기록 · 코드 개선 제안 블록과 tests/ 재현 스크립트(필요한 줄만) · 시작할 때와 단계마다 hand_off 그 섹션을 다시 읽는다
- 🔴 **테스트를 먼저 돌리고, 읽는 검토는 나중**: 관련 테스트 실행 → 결과 기록 → diff · 연결된 함수 · 클래스 읽기 → 성공 기준(C 번호)에 맞는지 검토 → 빠진 경우의 테스트 작성 · 실행 — 같은 모델이 짜고 읽으면 맹점이 같다 · 판정은 테스트 종료코드로
- **민감 섹션만** 서브 둘을 병렬로: 리뷰 서브(2-3 질문으로 diff 를 읽고 지적만) + 테스트 서브(성공 기준마다 테스트 작성 · 실행) · 지시에 «코드 수정 금지 · 실패한 테스트는 예상된 실패 표시(CODE_RULE 13절)로 tests/ 에 · 쓰는 중인 초안은 /tmp» · 합칠 때 판정 = 테스트 결과 · 리뷰 지적 = 더 확인할 후보 · 저위험은 서브 하나가 «테스트 → 리뷰»
- **범위 대조**: git log --name-only 섹션시작커밋..이번커밋(검증자 커밋 · docs 는 뺀다)이 바꾼 파일을 수정 범위 콜아웃 목록(변경 대상 + 생성 예정 + 승인된 변경 N)과 대조 → 상세 기록 «범위 대조» 줄 · 목록 밖 파일이 있으면 불일치 🔴
- 검증 정리표 = 카테고리별(API · UI · DB …) · 행 번호 «카테고리-번호» · 자연어 · 상세 기록 = 행 · 카테고리 · 대상 파일 · 대상 함수 · 기대 · 실제 · 일치(🔴/🟢) · 조치 · 조치 일시
- 코드 개선 제안 = 대상 파일 · 카테고리(함수 · 클래스 · 패키지 구조 · 모듈화 · 분기·경계값 · 예외 처리 · 동시성·중복 쓰기 · 하드코딩) · 문제점(개선 방향은 쓰지 않음) · 중요도(🔴 필수 · 🟠 잠재 위험 · 🟢 있으면 좋음) · 확신도 [확실 / 유력 / 의심] · 버그가 없으면 «없음» · «확인했지만 문제없던 항목» 도
- 실패 원인이 검증 범위 밖이면 git status 로 확인해 그대로 적는다(디버깅하지 않음) · 끝나면 검증 기록 · 개선 제안 · tests/ 를 경로로 커밋 → run

## 2-3. 리뷰 질문 — «이 코드에서 ~ 는 확인했나?»(리뷰 서브 지시문에 그대로 · ref/CHECKSHEET.md 2절과 같이)
- **함수** — 한 함수가 두 가지 일을 하지 않나? 이름과 하는 일이 맞나? 같은 입력에 같은 결과인가(숨은 전역 상태)?
- **클래스** — 여러 요청이 상태를 가진 객체 하나를 같이 쓰지 않나? 만들 때 외부 연결을 바로 열지 않나?
- **패키지 구조** — 화면 코드가 DB · 외부 API 를 직접 부르지 않나(CODE_RULE 3절 층 구분)?
- **모듈화** — 같은 계산 · 같은 규칙이 두 곳에 따로 있지 않나?
- **분기·경계값** — 0 · 음수 · 빈 목록 · 없는 키 · 최댓값 · 날짜 · 시간대 경계에서 어느 분기로 가나? else 가 조용히 삼키지 않나?
- **예외 처리** — 넓게 잡아 내부 오류를 외부 실패로 숨기지 않나? 실패 뒤 반쯤 된 상태가 남지 않나? timeout 을 «실패» 로 단정하지 않나(성공 · 실패 · 모름)? 오류 때 옛 결과가 화면에 남지 않나?
- **동시성·중복 쓰기** — (쓰기가 있고 중복 요청이 요구에 있을 때만) 확인과 쓰기 사이에 틈이 없나? 중복 금지 설정이 실제로 걸렸나? 재시도가 처음과 같은 요청 구별 키를 쓰나?
- **하드코딩** — 주소 · 키 · 대기 한도 · 경로 · 임계값이 코드에 박혀 있지 않나(설정 파일 · 환경변수)?
